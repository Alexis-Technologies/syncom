# Benchmarks

Every number on this page comes from scripts in the repository. The results are recorded in
[`bench/results/`](https://github.com/Alexis-Technologies/syncom/tree/main/bench/results), and
`pnpm bench:report` turns them into these charts and tables. They were measured on one machine,
named under each chart. Read them as relative guidance: the order and the orders of magnitude
carry over to other hardware, the exact figures do not. What each library can do, feature by
feature, is on the [comparison](/guide/comparison) page.

## Compared with other libraries

Nine libraries keep the same collection of small records (the to-do of every local-first demo:
a title, a flag, a priority, an owner, a counter) and are asked to do what an application does
with it. They insert a record into a store of 1,000, update a field, read a record, increment a
counter that converges, insert 1,000 at once, and replicate the whole store to an empty replica.
Each scenario runs twice: **in memory**, where nothing touches the disk, and **on disk**, where
every library uses its own persistence on `node:fs` and every write is awaited. Each library is
used the way its documentation shows; the adapters are in
[`bench/compare/adapters/`](https://github.com/Alexis-Technologies/syncom/tree/main/bench/compare/adapters).
Pick a scenario and a storage; hover over or focus a bar to see the time of one operation, the
spread of the samples and the exact version.

### How to read it

The libraries do different work for one call, so read the charts as a price list, not a ranking.

- **A syncom write does more.** A Yjs or Loro write changes a document in memory and, on disk,
  appends one update. A syncom write is an op appended to the op log, the record's own file,
  its catalog row and, unless `chain: false`, a block in the chain. That is four file writes
  per write with the chain and two without, and it is what lets a record be checked, purged,
  repaired, replicated by scope and queried. The `chain: false` rows show what the chain costs:
  between a third and a half of a write on disk.
- **Writes on disk are where syncom pays.** It does about 1,400 inserts a second (2,100 without
  the chain). The LevelDB-backed Yjs and PouchDB and Loro's single append do 19,000 to 26,000.
  syncom's own profile shows where half of that goes: after writes, the catalog is serialized
  whole, so a write costs more as the store grows. In memory, an insert into 1,000 records is
  three times as fast as one into 20,000. Saving the catalog incrementally is the open
  improvement. Further down the disk chart: TinyBase's file persister rewrites the whole store
  on every save (about 170 a second), Automerge's change cost grows with the document, and GUN
  waits for RAD's 250 ms flush before it acknowledges a write (about 4 a second).
- **Reads come from a cache.** syncom answers about 950,000 reads a second on both lines, each a
  JSON copy of the record. Automerge (10.6 million) and Yjs (3.7 million) read their
  materialized documents, and TinyBase reads 1.4 million. PouchDB (30,000 to 42,000), Fireproof
  (about 700) and OrbitDB (about 80) go to their storage; OrbitDB walks its log for every read.
- **Replication in memory is level with the CRDTs.** An empty syncom replica pulls 1,000 records
  at 100,000 to 112,000 a second, through the same path a WebSocket peer takes (hello, push, a
  feed of pages, JSON across the boundary). Loro manages 105,000 and Yjs 100,000; RxDB 64,000,
  Automerge 21,000, PouchDB 18,000 and TinyBase 11,500 come behind, and OrbitDB, over loopback
  TCP, 220. On disk the replica writes every record's file and one chain block per page, and
  manages 7,100 a second. That is behind Loro (108,000, one append), Yjs (54,000) and PouchDB
  (16,500), and ahead of TinyBase (11,100), Automerge (3,100) and OrbitDB (193).
- **Batches.** syncom has no batch write: 1,000 inserts are 1,000 ops, each appended on its own
  (36,000 a second in memory, 1,850 on disk). RxDB's in-memory `bulkInsert` (2.2 million) and
  a Yjs transaction (155,000 to 275,000) write the batch at once. GUN has no number: in two
  attempts, a batch of 1,000 concurrent puts left a write without its acknowledgement for 30 s.
- **Counters.** Loro's `LoroCounter` is the fastest (349,000 a second in memory, 43,000 on
  disk). syncom does 53,000 to 76,000 in memory and 1,700 to 3,500 on disk, and Automerge
  about 2,000. The others have no counter that converges, so they are not in this chart.
- **Cold start.** syncom opens a store of 1,000 records and reads one in 34 ms, the fastest here:
  its catalog is one JSON file, and nothing compiles WebAssembly or starts a network stack.
  Loro and TinyBase take about 51 ms, Yjs and PouchDB about 83 to 85 ms (LevelDB), Automerge
  183 ms (WebAssembly), Fireproof 240 ms and OrbitDB 577 ms (libp2p and Helia).

### Method

- **A fresh process for every pair.** Every (library, scenario) pair runs in its own process
  and its own temporary directory, so no library's JIT feedback, heap or open handles leak into
  the next measurement.
- **Checked before timed.** The store is seeded with 1,000 records first. Then the library must
  give the scenario's answers: a record reads back as it was written, an update shows, three
  increments make 3, a batch's last record reads back, a replica reads every one of the 1,000
  records. A mismatch aborts the run, because a call that does the wrong thing is fast and
  measures nothing.
- **One write in flight.** An operation that returns a promise is awaited before the next one,
  as an application that awaits its writes does. Operations are timed in chunks, so reading the
  clock does not dominate a call of a few hundred nanoseconds. After a one-second warmup, five
  one-second samples are taken and the median is reported. A sample stops after 5,000
  operations, so a fast library does not grow its store a hundred times larger than a slow one's.
  A batch or a replication is a round, timed five times after one warmup round.
- **On disk means each library's own persistence**, with its defaults: syncom on `node:fs`,
  y-leveldb, automerge-repo's NodeFS adapter, Loro's updates appended to a file (Loro ships no
  storage), TinyBase's file persister, PouchDB's LevelDB, Fireproof's `file://` store, GUN's RAD
  and OrbitDB's LevelDB. Nobody calls `fsync`: syncom's `durable` is off by default, and so is
  LevelDB's `sync`. RxDB is in memory only, because its Node.js disk storages are Premium.
- **Sync means each library's own protocol, in process.** syncom runs over the in-process link
  its tests use (JSON across the boundary, like a wrpc client). Yjs exchanges state vectors as
  y-protocols does, Automerge runs its sync protocol (two repositories on a MessageChannel, on
  disk), Loro exports from the replica's version, TinyBase uses two `LocalSynchronizer`s,
  PouchDB `PouchDB.replicate`, and RxDB `replicateRxCollection` with a pull handler. OrbitDB
  has no in-process transport, so its two nodes talk libp2p over TCP on 127.0.0.1. Fireproof
  syncs only through a cloud or a gateway, and GUN only over its WebSocket or WebRTC mesh, so
  neither takes part in that scenario.
- **The libraries are installed on their own.** They live in `bench/compare/package.json`,
  which `pnpm bench:compare:install` installs, so none of them is a dependency of syncom.

## Reproducing the numbers

```bash
pnpm bench:compare:install              # the libraries, into bench/compare/node_modules
pnpm bench:compare                      # every library and scenario, the cold start → bench/results/compare.json
pnpm bench:size                         # bundle sizes → bench/results/size.json
pnpm bench --save                       # syncom's own benchmarks → bench/results/engine.json
pnpm bench:report                       # the charts (docs/public/benchmarks) and the tables here and in the README
```

`pnpm bench:compare --only syncom,yjs --scenarios sync` measures a subset and merges it into
the existing results. `--samples`, `--sample-ms`, `--warmup-ms`, `--max-ops`, `--rounds` and
`--warmup-rounds` change the method, and `--cold-runs 0` skips the cold start.
