# Benchmarks

Every number on this page comes from scripts in the repository. The results are recorded in
[`bench/results/`](https://github.com/Alexis-Technologies/syncom/tree/main/bench/results), and
`pnpm bench:report` turns them into these charts and tables. They were measured on one machine,
named under each chart. Read them as relative guidance: the order and the orders of magnitude
carry over to other hardware, the exact figures do not. What each library can do, feature by
feature, is on the [comparison](/guide/comparison) page.

## Compared with other libraries

Nine libraries keep the same collection of small records (the to-do of every local-first demo:
a title, a flag, a priority, an owner, a counter) and are asked to do what an application does
with it. They insert a record into a store of 1,000, update a field, read a record, increment a
counter that converges, insert 1,000 at once, and replicate the whole store to an empty replica.
Each scenario runs twice: **in memory**, where nothing touches the disk, and **on disk**, where
every library uses its own persistence on `node:fs` and every write is awaited — typing into a
text too, which makes the disk line the durable one. Each library is
used the way its documentation shows; the adapters are in
[`bench/compare/adapters/`](https://github.com/Alexis-Technologies/syncom/tree/main/bench/compare/adapters).
Pick a scenario and a storage; hover over or focus a bar to see the time of one operation, the
spread of the samples and the exact version.

### How to read it

The libraries do different work for one call, so read the charts as a price list, not a ranking.
syncom runs as two builds. **syncom** is the pure CRDT: the core with the `text` and `sync`
plugins, no signatures and no chain, record files a frame behind the log (`defer: 16`) — what
an editor that only merges opens. **syncom-secure** is `@alexify/syncom/all`: every op signed
with the node's Ed25519 key, every write a block of the hash-linked chain — what a node of a
signed, hosted mesh opens.

- **A syncom write does more.** A Yjs or Loro write changes a document in memory and, on disk,
  appends one update. A syncom write is an op appended to the op log; its record file and
  catalog row land within the deferred window, and in the secure build it is also signed and
  chained. That is what lets a record be queried, replicated by scope, purged and repaired —
  and, signed, verified by every peer. In memory the pure build inserts about 43,000 records a
  second and the secure one about 15,000: signatures and the chain cost about two thirds of a
  write there. A peer's page is verified on Node's thread pool — about 36,000 ops a second
  (the `verifyOp` row of [syncom's own](#syncom-s-own-benchmarks) benchmarks).
- **New records on disk are where syncom pays.** About 5,400 inserts a second (4,300 secure),
  where the LevelDB-backed Yjs and PouchDB and Loro's single append do 18,000 to 23,000: every
  new record is a file of its own, written within the deferred window. A change to a record that
  is there costs a line appended to the log's journal and, once per window, the record's file:
  updates and increments run at about 22,000 a second (7,000 to 7,400 secure), beside Yjs
  (20,000), ahead of PouchDB (8,300), behind Loro (39,000 to 40,000). Further down the disk chart:
  TinyBase's file persister rewrites the whole store on every save (about 170 a second),
  Automerge's change cost grows with the document, and GUN waits for RAD's 250 ms flush before
  it acknowledges a write (about 4 a second).
- **Reads come from a cache.** syncom answers 850,000 to 890,000 reads a second on both lines,
  each a JSON copy of the record. Automerge (about 10 million) and Yjs (3.8 million) read their
  materialized documents, and TinyBase reads 1.3 to 1.4 million. PouchDB (29,000 to 39,000),
  Fireproof (about 700) and OrbitDB (about 80) go to their storage; OrbitDB walks its log for
  every read.
- **Replication.** An empty replica of the pure build pulls 1,000 records at about 73,000 a second
  in memory, through the same path a WebSocket peer takes (hello, push, a feed of pages, JSON
  across the boundary) — behind Loro (101,000) and Yjs (100,000), ahead of RxDB (59,000). The
  secure build checks every op's signature on the way in and pulls about 22,000. On disk the
  replica writes every record's file too: 6,500 a second (5,400 secure), behind Loro (95,000,
  one append), Yjs (49,000), PouchDB (15,000) and TinyBase (11,000), ahead of Automerge (3,000).
- **Batches.** syncom has no batch write: 1,000 inserts are 1,000 ops (about 41,000 a second in
  memory, 6,300 on disk — the ops group into one log line each while a write is in flight).
  RxDB's in-memory `bulkInsert` (1.9 million) and a Yjs transaction (145,000 to 217,000) write
  the batch at once. `transact()` writes several records as one append when they belong together.
- **Counters.** Loro's `LoroCounter` is the fastest (307,000 a second in memory, 40,000 on disk).
  syncom does 109,000 in memory (19,000 secure) and 23,000 on disk (7,400 secure), and Automerge
  about 1,100 to 1,800. The
  others have no counter that converges, so they are not in this chart.
- **Cold start.** syncom opens a store of 1,000 records and reads one in about 57 ms (65 ms
  secure, which loads its key pairs), the fastest here: its catalog is one JSON file, and nothing
  compiles WebAssembly or starts a network stack. TinyBase and Loro take about 62 ms, Yjs and
  PouchDB 95 to 102 ms (LevelDB), Automerge 203 ms (WebAssembly), Fireproof 276 ms and OrbitDB
  649 ms (libp2p and Helia).

### Lists and text against the CRDT libraries

Three of the scenarios type into a text: one character at the end (the common keystroke), at the
start (every insert anchors into the same spot) and anywhere (seeded). Only the libraries with a
text that merges by position take part — syncom's text field, `Y.Text`, Automerge's text,
`LoroText`; the databases and the stores show "—". A syncom keystroke awaited is an op appended
to the log, its text a copy-on-write rope (O(log n) per keystroke), the record file written once
per deferred window. In memory the pure build types about 74,000 characters a second at the end, 48,000 at the start and 38,000 at random — ahead of Automerge (21,000 to 23,000), ahead of Yjs at random (28,000) — where Yjs types 342,000 to 461,000 at either end and Loro 294,000 to 609,000; the secure build, signing every keystroke, types 13,000 to 18,000.

**Typed through a handle** (`syncom · typed through openText()`), what an editor binding does:
each keystroke is made at once over the handle's reading, and the edits are logged a window
later as one transaction, keystrokes that continue each other — a word typed backward too — as one op; the row awaits the handle's flush every 1,024 keystrokes, so the log's cost is in its rate. It types about 322,000 characters a second at the end in memory (Yjs 342,000, Loro 609,000), 94,000 at the start and 40,000 at random; on disk 262,000 at the end — the fastest durable keystroke here, six times Loro's append (40,000) and fourteen times y-leveldb (19,000) — 93,000 at the start and 41,000 at random.

**On disk** is the durable line: every keystroke awaited until the library reports it stored —
y-leveldb's `storeUpdate`, Loro's update appended to a file, automerge-repo's flush, syncom's log
append. syncom types 30,000 characters a second at the end and 21,000 to 25,000 elsewhere (a keystroke elsewhere is a new run, written with the newest piece of the record's file once per window; 9,600 to 12,000 secure), Automerge about 2,900, Yjs 12,000 to 21,000 and Loro about
40,000.

The editing-trace benchmark the CRDT libraries publish (automerge-perf: 259,778 keystrokes of a
real paper, 182,315 inserts and 77,463 deletes) runs as the `trace` scenario: the whole trace
replayed into one text as an editor sends it — one keystroke after another, not waiting for
each — and the text read back whole at the end. The pure build replays it in 1.6 seconds (158,000 keystrokes a second; 170,000 through a handle; 6.8 seconds secure), Yjs in 5,
Automerge in 15 and Loro in half a second. The JS heap the trace leaves is about 23 MB for
syncom — the engine's text is 8 MB of it, the rest the trace's log held in memory (its entries,
and the files of the `memory()` backend) — and 4 MB for Yjs (Automerge's and Loro's live in
WebAssembly memory, which that number does not count). The trace is downloaded at
bench time, not redistributed (CC-BY-4.0).

**With every change encoded.** Yjs encodes an update only while something listens to the
document, and Loro exports nothing at a commit unless something subscribes — while a syncom
write in memory is still an op appended to its log. Two more rows, in memory only, run the same
documents with that work done, as a provider or a persistence would: Yjs with an `update`
listener, Loro with `subscribeLocalUpdates`. Loro then types 87,000 to 107,000 characters a
second wherever it types and replays the trace at 98,000 keystrokes a second; Yjs types 26,000
to 251,000 and replays the trace at 46,000.

### Lists against the CRDT libraries

Five scenarios edit a list of 10,000 numbers: push one, insert one at a random index, remove one
at a random index (and push one, so the list keeps its length — one op is both), give one a new
value, move one. Only the libraries with a list that merges by position take part — syncom's
list field, `Y.Array`, Automerge's list, `LoroList` (`LoroMovableList` for set and move, the
list Loro's documentation gives for both); `Y.Array` has no element of its own to set and no
move, Automerge's list no move. In memory the pure build makes 20,000 to 48,000 edits a second (7,900 to 16,000 secure) — a list op costs O(log n), its reading made when it is read, as the
50,000-element rows of syncom's own benchmarks below show — ahead of Yjs at push and remove
(Yjs 2,200 to 26,000), Automerge 1,500 to 5,500 and Loro 230,000 to 520,000 (49,000 to 107,000
with every commit exported). On disk syncom makes 8,600 to 17,000, Yjs 2,100 to 12,000,
Automerge 850 to 2,200 and Loro 20,000 to 42,000.

### Method

- **A fresh process for every pair.** Every (library, scenario) pair runs in its own process
  and its own temporary directory, so no library's JIT feedback, heap or open handles leak into
  the next measurement.
- **Checked before timed.** The store is seeded with 1,000 records first. Then the library must
  give the scenario's answers: a record reads back as it was written, an update shows, three
  increments make 3, a batch's last record reads back, a replica reads every one of the 1,000
  records. A mismatch aborts the run, because a call that does the wrong thing is fast and
  measures nothing.
- **One write in flight.** An operation that returns a promise is awaited before the next one,
  as an application that awaits its writes does. Operations are timed in chunks, so reading the
  clock does not dominate a call of a few hundred nanoseconds. After a one-second warmup, five
  one-second samples are taken and the median is reported. A sample stops after 5,000
  operations, so a fast library does not grow its store a hundred times larger than a slow one's.
  A batch or a replication is a round, timed five times after one warmup round.
- **On disk means each library's own persistence**, with its defaults: syncom on `node:fs`,
  y-leveldb, automerge-repo's NodeFS adapter, Loro's updates appended to a file (Loro ships no
  storage), TinyBase's file persister, PouchDB's LevelDB, Fireproof's `file://` store, GUN's RAD
  and OrbitDB's LevelDB. Nobody calls `fsync`: syncom's `durable` is off by default, and so is
  LevelDB's `sync`. RxDB is in memory only, because its Node.js disk storages are Premium.
- **Sync means each library's own protocol, in process.** syncom runs over the in-process link
  its tests use (JSON across the boundary, like a wrpc client). Yjs exchanges state vectors as
  y-protocols does, Automerge runs its sync protocol (two repositories on a MessageChannel, on
  disk), Loro exports from the replica's version, TinyBase uses two `LocalSynchronizer`s,
  PouchDB `PouchDB.replicate`, and RxDB `replicateRxCollection` with a pull handler. OrbitDB
  has no in-process transport, so its two nodes talk libp2p over TCP on 127.0.0.1. Fireproof
  syncs only through a cloud or a gateway, and GUN only over its WebSocket or WebRTC mesh, so
  neither takes part in that scenario.
- **Two rows encode every change.** `Yjs · every update encoded` and `Loro · every commit
  exported` are the memory documents with an `update` listener and `subscribeLocalUpdates`:
  the work an application that persists or syncs the document has done for every write. They
  run in memory only — on disk the Yjs and Loro rows store every update already.
- **The libraries are installed on their own.** They live in `bench/compare/package.json`,
  which `pnpm bench:compare:install` installs, so none of them is a dependency of syncom.

## syncom's own benchmarks

`pnpm bench` runs one script per subject in `bench/`: the storage API end to end, a peer's
page as it is applied, replication over the in-process link, full-text search, the op log, the
chain, hashing, the CRDT helpers, the emitter, and the list and text engine — a keystroke, a
reading, a hydration, and the same at a size where a cost per element would show: a text under
5,000 marks, a list of 50,000 elements, a run typed 200,000 characters long, the first op on a
record read from its JSON. They are the numbers to watch for a regression, and `pnpm bench --save`
records them.

## Reproducing the numbers

```bash
pnpm bench:compare:install              # the libraries, into bench/compare/node_modules
pnpm bench:compare                      # every library and scenario, the cold start → bench/results/compare.json
pnpm bench:size                         # bundle sizes → bench/results/size.json
pnpm bench --save                       # syncom's own benchmarks → bench/results/engine.json
pnpm bench:report                       # the charts (docs/public/benchmarks) and the tables here and in the README
```

`pnpm bench:compare --only syncom,yjs --scenarios sync` measures a subset and merges it into
the existing results. `--samples`, `--sample-ms`, `--warmup-ms`, `--max-ops`, `--rounds` and
`--warmup-rounds` change the method, and `--cold-runs 0` skips the cold start.
