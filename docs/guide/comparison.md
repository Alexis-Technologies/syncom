# Compared with alternatives

syncom is a data engine that keeps records on the device and replicates them between nodes. That
puts it where four kinds of tools meet: the **CRDT libraries** (Yjs, Automerge, Loro), which
merge documents and leave storage and queries to you; the **local-first databases** (Jazz, RxDB,
PouchDB, TinyBase, Dexie Cloud, Fireproof), which store and query records and sync them through a
backend;
the **peer-to-peer and event-sourced stores** (GUN, OrbitDB, Evolu, LiveStore); and the **sync
services** (ElectricSQL, PowerSync, Zero, Triplit, InstantDB), which replicate a server database to
clients. The table compares syncom with eighteen of them, with every feature in one table rather
than a few favourable rows. syncom is the first column. It is tinted, and on a wide screen it stays
pinned next to the features while the table scrolls, so every row can be read against it.

How fast each one is, measured on the same scenarios, is on the [Benchmarks](/guide/benchmarks)
page. RxDB, the closest of them, is compared with syncom feature by feature, in 300 rows, on
[Compared with RxDB](/guide/vs-rxdb), and the three CRDT libraries, as CRDT libraries only, in 141
rows on [Compared with CRDT libraries](/guide/vs-crdt).

## What the table shows

- **A database or a merge, rarely both.** The CRDT libraries merge text and lists
  character by character, but they have no queries, no indexes and no schema (Loro has
  partial ones). The databases and services do query, but most of them resolve a conflict
  per document or per revision, or let the server decide. syncom sits between the two. It
  gives you records with a schema, Mango queries, indexes and unique keys, and it merges
  concurrent writes field by field, with counters that add up — and its list and text fields
  merge by position (Fugue), with marks, cursors and moves, its trees move without cycles, and
  it carries what the CRDT libraries carry around a document: a history read at any version,
  named versions, an undo that converges, branches that merge back. That makes it a database
  that merges, not a document CRDT: no editor bindings, and a text is a field of a record, not
  a document.
- **Few sync without a server of their own and still check what they receive.** Nine of the
  nineteen need no server from the project to sync: syncom, Yjs, Automerge, Loro, RxDB,
  PouchDB, TinyBase, GUN and OrbitDB. Of those nine, only syncom and RxDB validate writes
  against a schema. Only RxDB and PouchDB let the node serving the data reject a write before it
  spreads (RxDB through its server plugin, PouchDB through CouchDB's `validate_doc_update`). A
  syncom host runs the same validators, hooks and scopes on a peer's op that it runs on its own
  writes, but it still relays an op its validator or hook skipped, so every node behind it judges
  that op for itself; only out-of-scope and unsigned ops stop at the host.
- **Counters that converge are rare.** syncom, Automerge, Loro, Jazz and Dexie Cloud have them;
  Jazz sums the deltas on its server, Dexie Cloud replays the operation on its. Everywhere else, two replicas that increment the
  same number at the same time lose one of the increments.
- **A history that cannot be altered usually cannot be purged either.** Four keep a
  tamper-evident history: syncom, Automerge, Fireproof and OrbitDB. Automerge, Fireproof
  and OrbitDB cannot take a payload back out of it. syncom's `purge()` removes the payload
  from the op log and keeps the record of the operation; Jazz 2.0 keeps every version of a row
  and has no purge.
  Zero, Triplit, InstantDB and TinyBase can delete for good because they keep no history to
  begin with.
- **Unique keys across replicas.** Only syncom and InstantDB enforce a unique key. syncom
  checks it on every write and reports a clash between two peers as a `conflict` event. In the
  others the key is per device, or it is checked only where the server writes to Postgres.
- **Where syncom is behind.** It has no editor bindings and no document-scale text (Yjs,
  Automerge and Loro have both; syncom's text is a field of a record). End-to-end encryption is a recipe, field by field (Evolu encrypts everything it
  syncs; Jazz 2.0 ships encryption adapters, not yet wired into its tables). There are no UI bindings and no React Native target, and it is
  not yet on npm.
- **Some are no longer moving, or are moving away.** PouchDB has not published since June 2024,
  and GUN's npm release is from July 2025. Triplit's last release was July 2025 and its site is
  gone. Instant Cloud closed to new signups and shuts down on 2027-08-31; InstantDB stays open
  source for self-hosting. Jazz's npm `latest` (0.20, Jazz Classic) is a product its
  maintainers call legacy; the table compares 2.0 (alpha), as the method below says.

## How the table was made

- **From the code, not the README.** Each library was read at its latest npm version in
  October 2026: the published tarball, plus the official docs. Where the docs and the code
  disagree, the cell follows the code and a footnote says so. A service is judged as client
  and server together; the cell says which side a feature lives on.
- **Which version.** A library is compared at its npm `latest`, except when the project's site
  documents a later published version as current and treats `latest` as legacy: the Version row
  then names both and a footnote gives the lag (Jazz).
- **What ✅ means.** A feature counts as ✅ only when it ships in the project's own packages,
  and the package is named in the cell. A third-party package, a paid tier or an experimental
  flag makes it ⚠️, with the reason given.
- **The syncom column is this repository** at the version on the page, checked against
  its tests.
- **The data is in the repository.**
  [`docs/comparison.json`](https://github.com/Alexis-Technologies/syncom/blob/main/docs/comparison.json)
  keeps every cell with the file or page it was decided from, so you can check any of them.
  `pnpm docs:comparison` renders it into this page. If a cell is wrong, open an issue or edit
  the data; the table is generated from it.

5. npm lags the repository: master has commits through October 2026, but nothing has been published since July 2025.

8. The open-source core limits open collections across the process: the docs say 13; in the code (<code>src/rx-collection.ts:258-262</code>) the 14th opens after a delay of about 1.8 s and the 15th throws <code>COL23</code>. RxServer (<code>rxdb-server</code>) is SSPL.

22. A snapshot merge (bootstrap) and an op from a newer schema version (<code>ahead: 'apply'</code>, the default) are applied unvalidated, and a record outside any collection has no validator.
23. Documents are validated only when the storage is wrapped with a validator plugin.
24. A cell that fails the schema is dropped or defaulted silently, and schematizers keep only type, enum and default.
25. Mutations accept already-validated values: Evolu does not run the column validators on insert/update, nor on received changes.
26. The client <code>Schema</code> does not validate writes (mismatched types are silently CAST); validation is your backend's on upload, and a rejected write is rolled back at the next checkpoint.
27. <code>createSchema</code>/<code>table().columns()</code> only type ZQL and declare relationships: the client's <code>insert</code>/<code>update</code> store values unchecked, and Postgres checks them when the server mutator commits.
28. Adding, removing or renaming a column invalidates every shape on that table, so clients get <code>409</code>/<code>must-refetch</code>, drop their local copy and re-sync from scratch.
29. <code>Documents.get(key)</code> also walks the oplog from the head, so reads cost O(log length).
30. Two clients can commit events that collide; a materializer that then fails rolls back that event, which the docs say will 'typically halt' the system.
31. Fields of a record, not whole documents: a record is read and written whole per op, and a long document is a list of block records. No editor bindings yet.
32. <code>add([x])</code>/<code>remove([x])</code> merge across sync but return a sorted array, so element order is not kept.
33. A counter that one node resets while another increments it does not converge to the intuitive value; see Guarantees and limits in the Sync guide.
34. A number in a <code>Y.Map</code> is a register: of two concurrent increments, one is lost.
35. Increments add up only if the server mutator applies them atomically (raw SQL <code>n = n + 1</code>, or <code>serializable</code> + <code>tx.retryOn</code>); the default isolation is Postgres <code>read committed</code>.

38. The compressed document still carries the full change history — Automerge does not drop history.
39. Compaction copies every block the clock reaches into the new CAR, so a newcomer still downloads the history.
40. Docs still call compaction planned, but the code has it behind an undocumented <code>experimental_compaction</code> shape param (default false), so by default a newcomer replays the snapshot plus every change since the shape was created.
41. Not wall-clock LWW: a concurrent <code>Y.Map</code> set is won by the writer with the higher random <code>clientID</code>, whatever the times.
42. The winner is chosen by operation id (counter, then actor), not wall-clock time; <code>getConflicts</code> returns the losing values.
43. The docs say the edit Core receives first wins; the spec and its invariant tests say the last write Core accepts wins per cell. The spec is followed here.
44. A whole-object <code>put()</code> overwrites concurrent property updates; <code>where().modify()</code> is re-run on the server.
45. Order comes from each writer's machine clock (<code>+new Date</code>): a write stamped in the future is held in a <code>setTimeout</code> until then and wins; equal states break by comparing JSON strings.
46. A change stamped more than 5 minutes ahead of the receiver's clock is quarantined until system time catches up.
47. Merge-conflict handling isn't implemented yet (#253): concurrent events simply apply in the backend's order.
48. The client never merges: it holds its checkpoint while uploads are pending, then adopts the server's checkpoint exactly; plain UPDATEs in the backend give per-field LWW by arrival order.
49. No field-level merge: the server re-runs each mutator against current Postgres state, so concurrent writes to a column are last-processed-wins unless your mutator checks.
50. The FAQ still describes per-attribute HLC timestamps from 0.x. In 1.x the server stamps each incoming batch with its own clock when it arrives, so an edit made offline hours ago overwrites newer values when it finally syncs.
51. Order is server arrival, not a timestamp: an offline write replayed on reconnect overwrites newer writes made meanwhile.
52. Ops written before any node was registered, and compacted since, cannot reach a host (<code>UNDELIVERABLE</code>).
53. Reconnect re-sends only queued messages held in memory and live <code>get</code>s; there is no persisted outbox, and src/websocket.js:5 still reads 'TODO: resync upon reconnect'.
54. Writes queue only while <code>connecting</code> (<code>disconnectTimeoutMs</code>); docs-vs-code: the shipped client also accepts writes in <code>needs-auth</code>, which the docs list as rejected.
55. A withheld op would leave a gap in its origin's stream, so a host that skips an op still relays it and every node re-checks it; a throwing <code>beforeApply</code> refuses the whole page instead.
56. <code>middleware</code> on the server's own MergeableStore guards only that copy; <code>WsServer</code> still relays the message to the other clients.
57. A rejected incoming entry is caught and only <code>console.error</code>'d; the app gets no event for it.
58. Whoever can write the directory can rebuild the chain; a read checks a record against the block its file names, so a block planted beside the chain passes. The ops in the log are what is signed.
59. The default <code>'verify'</code> takes an unsigned op; <code>sync.signatures: 'require'</code> refuses it. A bootstrap re-signs the host's state under the joiner's key, and <code>hello</code> does not yet prove possession of the key.
60. Only data under a user's <code>~pubkey</code> soul is signed and verified; the public graph accepts unsigned writes from anyone.
61. A backend wrapper from <code>@alexify/syncom/encryption</code>: the key is given or derived from a password and a salt, never written; the sealed-record form (one record for this node's RSA pair, outside the log) is the other block of the same subpath.
62. The free plugin is AES-CBC in crypto-js's passphrase mode (MD5 key derivation, no MAC); an unsalted SHA-256 of the password is stored beside the data.
63. The Loro team says not to rely on it for production-grade security yet.
64. The encryption wrapper sits below <code>collection.storageInstance</code>, which is what the replication reads.
65. Needs the encryption middleware moved above sync by hand; indexed fields are not encrypted.
66. <code>MetaGateway.put</code> attaches the ledger's key material to every meta update, so the sync service holds the key although the docs call sync end-to-end.
67. In 4.0.0 the <code>documents</code> type destructures <code>encrypt</code> instead of <code>encryption</code>, so document stores silently stay unencrypted (issue #1253, fix PR #1257 open).
68. Peer ids are self-asserted in the WebSocket join message, so access by peer id needs authentication at the socket.
69. RxServer is SSPL and its defaults are open: with no <code>authHandler</code> every request is admitted, and the Express adapter's CORS reflects any origin with credentials.
70. CouchDB has no per-document read rules; the usual pattern is a database per user.
71. Anyone who knows a database address can replicate and read it unless it is encrypted.
72. Electric serves any data its Postgres role can read to any caller; <code>ELECTRIC_SECRET</code> must be added by a proxy that also pins the shape's table and <code>where</code>.
73. A rule that is not set evaluates to true: everything is open until you write rules.
74. The chain keeps an unsalted SHA-256 of every version of the record, which can confirm a guessed record.
75. GC clears the document state only; update logs kept by providers or peers hold the payload until they compact (<code>y-indexeddb</code> merges after 500 updates).
76. A shallow snapshot only syncs with peers past its start version, and other replicas keep their full history.

## Where each one fits

- **syncom**: records with a schema, queries and live views, kept on the device and replicated
  between servers, browsers and peers. Any node can host, so no service is needed, and the
  history is verifiable and can be purged. Zero dependencies.
- **Yjs, Automerge, Loro**: collaborative editing. Text, rich text, lists and trees merge
  character by character; storage, queries and access control are yours. Yjs has the largest
  ecosystem of editor bindings, Automerge keeps the full history, and Loro has the richest
  container types.
- **Jazz**: a local-first relational database (2.0): typed tables, queries with joins and
  aggregates, row-level policies, history and branch views — merged by its server, so it needs one
  (Jazz Cloud or a self-hosted `jazz-napi`).
- **RxDB**: a reactive JSON-document database with many storages and replication plugins. Disk
  storage on Node.js and several features are Premium.
- **PouchDB**: CouchDB's replication protocol in the browser, with a CouchDB as the hub.
- **TinyBase**: a small reactive in-memory store with many persisters and a simple sync protocol.
- **Dexie Cloud**: IndexedDB with a hosted (or licensed on-prem) sync service, realms and roles.
- **Fireproof**: an encrypted, content-addressed document ledger that syncs through its cloud.
- **GUN, OrbitDB**: peer-to-peer graphs and logs, over GUN's own mesh or libp2p and IPFS.
- **Evolu**: end-to-end encrypted SQLite on the device, synced through a blind relay.
- **LiveStore**: event sourcing into SQLite on the client, with a central sync backend.
- **ElectricSQL, PowerSync, Zero**: Postgres (or MongoDB, for PowerSync) is the source of truth.
  Clients get shapes, buckets or query results, and writes go through your API.
- **Triplit, InstantDB**: a sync database with its own server, query language and permissions.
